The Google Workspace connector supports [automatic account provisioning and deprovisioning](/product/admin/account-provisioning).

The connector also supports group creation (via the `create_group` connector action) and deletion, [continuous sync](/baton/faq#syncing), and targeted sync for accounts, groups, and roles.

Continuous sync streams sign-in activity, app usage, and admin audit events between full syncs, so last-login data and membership changes stay current. It requires the `admin.reports.audit.readonly` scope.

The synced user profile exposes the job title under both `title` and `job_title`, for backward compatibility. `update_user`'s `user_profile` JSON object accepts any of `job_title`, `jobTitle`, or `title` as the source key. `update_user_profile` has a fixed argument schema and only exposes `job_title` — pass the value under that key.
</Note>

<Note>
`update_user_profile` and `update_user` never clear an assigned manager, matching the behavior of `update_user_manager`. An empty or invalid `manager_email` is not applied. Unlike other invalid fields, it does not fail the whole call as long as one other provided field is valid.

Both actions return `skipped_fields`, a comma-separated list naming any provided field that was not applied and why. That evidence is also retained if the profile update fails. A response of `success: true` means the call completed, not that every requested field was applied; check `skipped_fields`. `update_user` also returns `updated_fields`, naming the requested changes, not independently verified postconditions. Use a targeted user resource read when independent current-state confirmation is required. Read-modify-write updates require an observed ETag and send it in `If-Match`; missing versions fail before writing and provider precondition errors are preserved. Directory does not document conditional-write enforcement for [users.update](https://developers.google.com/workspace/admin/directory/reference/rest/v1/users/update) or [users.patch](https://developers.google.com/workspace/admin/directory/reference/rest/v1/users/patch). Fixtures prove header emission, not tenant concurrency protection; protection against concurrent overwrites remains an unverified provider integration gate.
</Note>

### Account preparation and password management

Account creation accepts the optional boolean `suspended` and string `org_unit_path`. Both are applied in the initial Google user insert, so `suspended: true` does not create an active account and disable it later. The OU path must be absolute, such as `/Prehires`. Omitting either option preserves Google's existing creation defaults.

Creation and credential rotation support SDK-generated passwords and encrypted supplied passwords. Supplied password bytes are passed through after SDK decryption and are not returned. Generated passwords honor the requested SDK length and constraints and return through the SDK encrypted-result mechanism. Configure encrypted result recipients before requesting generation; generating a password does not itself establish storage or delivery. Supplied-password input cannot be combined with returned-credential encryption configurations.

Existing-account rotation uses the credential-management interface, not a connector action accepting a password argument. The credential option `force_change_at_next_login` sets or clears Google's next-login requirement. Creation also retains the existing `changePasswordAtNextLogin` profile option. These requirements apply to direct Google authentication, not sign-in through a third-party identity provider. Do not infer SSO readiness or employee takeover from a password flag.

### Observed resource state and partial results

Targeted user reads and user sync pages expose `google_user_state` on the resource profile. It includes provider identity and reported `suspended`, `archived`, `change_password_at_next_login`, `is_mailbox_setup`, `aliases`, and `non_editable_aliases` facts. An omitted field is unknown, not false or empty. Read time belongs in the caller's observation receipt, not a persisted profile clock. Configured filter exclusions use gRPC `NotFound` with standard `ErrorInfo` reason `RESOURCE_FILTERED`, domain `baton-google-workspace`, and the filter type; point-read consumers must inspect that qualifier rather than infer provider absence. Genuine provider permission errors and malformed successes remain errors.

This changes the direct user `Get` hook for configured exclusions from no resource/no error to qualified `NotFound`. In pinned baton-sdk v0.29.0, `pkg/connectorbuilder/resource_syncer.go:GetResource` already converted the old nil resource to `NotFound`, and `pkg/sync/syncer.go:getResourceFromConnector` skips that code. Public skip classification is preserved, not newly introduced. `TestGoogleFilteredReadQualifierSurvivesSDKAndGRPC` separately verifies that `NotFound` and its added `RESOURCE_FILTERED` detail survive the local SDK/gRPC boundary. Transport evidence does not establish that every lifecycle host inspects the qualifier. Callers must inspect it before making absence decisions; that host integration is not implemented or certified here. SDK upgrades must rerun the transport fixtures and recheck the targeted-sync consumer. Existing resource/grant identities and normal List filtering are unchanged.

Targeted group reads optionally expose `group_settings` and `group_settings_status`. The status is `observed`, `unsupported`, or `unknown`; a missing scope or denied settings read must not be interpreted as a privacy setting being false. Normal group listing does not fetch settings for every row. Group settings require the existing Groups Settings API scope. `allow_web_posting` controls the web forum, not permission for external email senders.

`modify_group_settings` retains observed `previous_*` and requested `new_*` values even when the settings write fails. Requested values are not verified post-state; only a successful independent readback confirms the requested settings. Unknown write outcomes are not replayed by the handler.

User and group resource profiles contain stable provider facts, not connector-generated observation clocks. Identical provider reads produce identical resource payloads; C1's owning observation receipt records when the read occurred.

OAuth-token and application-password deletion results retain `deleted_ids`, `already_absent_ids`, `failed_ids`, `skipped_ids`, and `remaining_ids`, together with `inventory_complete` and `observed_at`. A blank skipped ID means an entry could not be identified. Cancellation stops subsequent revocations and final enumeration, retains completed per-item results, and returns a cancellation error with incomplete inventory; unattempted entries are not labeled as missing identities. If final enumeration fails, an empty `remaining_ids` list is not evidence of absence. Failed actions retain these partial results; consumers must preserve both the error and the result. These are observations at that instant, not proof of global session invalidation. Application grants derived from login activity are not a current credential inventory.

Group membership remains on the existing grant interface. Conflict reconciliation uses an exact member lookup, not a whole-group scan. The connector does not expose an independent point-grant action; callers must not replace unavailable bounded evidence with an incomplete membership enumeration.

### Transfer and alias evidence

Transfer submission is an acknowledgement, not completion. Retain the returned nonempty `transfer_id` and the approved source, recipient, application, and parameters. Use `get_user_data_transfer` for later observations; do not re-run a mutation to poll or blindly replay an unknown or completed attempt. Discovery of existing ongoing transfers is bounded to ten pages. Conflicting, ambiguous, or incomplete discovery fails before an insert. Historical completed records are not adopted as a new operation's result.

Drive privacy inputs remain case-insensitive and default to both private and shared; the connector sends Google's uppercase `PRIVATE`/`SHARED` values. The read action requires an explicit privacy list so verification cannot silently expand the approved scope. Calendar verification requires an explicit `release_resources`; an empty parameter set represents the documented retain-resources default. `completed` is true only after the saved identity and parameters match and both overall and per-application statuses report completion. Failed, missing, and unknown statuses are not completion.

A saved-ID or expected-owner mismatch returns only the requested transfer ID, observation time and false success/completion flags, not unrelated observed owners, status or parameters. Identity-matching parameter mismatches retain observed evidence for reconciliation. `pending`, like `new` and `inProgress`, is ongoing rather than completed.

Calendar Data Transfer covers future, non-private events in the source user's primary calendar with a guest or resource. It does not migrate all past, private, or secondary-calendar content. Operation completion is not independent per-file ownership or reservation-release evidence. Required broader postconditions need separate verification.

Alias removal uses the dedicated alias collection before and after a deletion, not absence of an optional user-profile field. It rejects primary addresses, known non-editable aliases, account-precondition changes, and an alias resolving to a different user. `alias_present_after` is omitted when readback is unknown. An alias absent from the selected account is not proof that the address is globally available; another user, group, or namespace may own it.

### Requestable alias creation

`add_user_alias` is a user-resource action using the existing Directory API user-provisioning scope. Both alias actions require a concrete configured Google customer ID, not the `my_customer` selector; no new scope/service is added to resolve selectors. They compare the observed customer with that configured boundary before alias collection or mutation, independently of submitted account pins. The add action also requires a stable Google user ID rather than an email or alias selector, plus the expected current primary email and customer ID. The provider enforces whether the alias namespace belongs to that customer. Provider-verified secondary domains are supported even if they differ from the connector's sync-selection domain; that filter is not an alias authorization policy.

Success requires observed attachment in the same pinned account's dedicated alias collection, not merely an accepted insert. `already_present` is an attachment-only, zero-write same-account replay, including a response where the alias appears in both that collection and `NonEditableAliases`; it does not make the alias editable. New insertion/replacement of a noneditable-only alias remains rejected. A conflicting user, group, or namespace never triggers deletion, transfer, or adoption. Primary addresses are rejected. Provider permission failures and uncertain readbacks remain errors with qualified evidence; configured-customer denials do not expose unrelated foreign-account fields.

Inspect `alias_present_before` and `alias_present_after`; an unread observation is omitted rather than reported false. `observation_complete` describes the alias post-state observation, not the absence of an error. `insert_attempted` records that the insert was attempted; `insert_acknowledged` records provider acknowledgment, not confirmed attachment. A false acknowledgment is not proof that no mutation occurred. Preserve those fields and the error when readback is unknown, and do not blindly replay an uncertain insert.

<Warning>
**A connector action does not grant self-service permission.** An administrator may expose it through an existing C1 requestable Action, but must bind the target account from the authorized requester/resource relationship and enforce the permitted alias/domain and approval policy through the Action's audience, policy, and trusted form/resource bindings. A user-supplied `user_id`, primary-email pin, or customer pin is not authorization evidence. The connector neither infers requester identity nor implements a new C1 approval system.

Publishing the connector capability does not automatically create or enable a customer-facing Action. Configuration tests proving that a requester cannot substitute another target or escape the administrator's alias/domain policy are separate from connector fixtures. No C1 requestable-Action UI/backend change, deployment, or live provider certification is claimed here.
</Warning>

## Before you begin

This connector authenticates with a **service account and domain-wide delegation**, not per-user OAuth. Every call reaches Google as one service account impersonating a Workspace super admin.

You need:

- **Permission to create the project**, if you are creating a new one: **Project Creator** (`roles/resourcemanager.projectCreator`), granted at the organization or folder level. A project-level role cannot create a project. Skip this if you are using an existing project.
- **Google Cloud roles on the project.** **Owner** covers everything else. Otherwise, grant three roles: **Service Usage Admin** (`roles/serviceusage.serviceUsageAdmin`) to enable APIs, **Service Account Creator** (`roles/iam.serviceAccountCreator`) to create the service account, and **Service Account Key Admin** (`roles/iam.serviceAccountKeyAdmin`) to create its JSON key. These roles belong to you, the person doing the setup. The service account itself needs no project role. See [Allow service account key creation](#allow-service-account-key-creation).
- **A Google Workspace super admin** to authorize domain-wide delegation and to act as the impersonated administrator.
- Either the **Connector Administrator** or **Super Administrator** role in C1.

<Warning>
**Check your organization's key policy first.** Google organizations created on or after May 3, 2024 block service account key creation by default. The connector requires a JSON key, so confirm you can create one before you start. See [Allow service account key creation](#allow-service-account-key-creation).
</Warning>

### What the Google Cloud project provides

| What | Why it matters |
| :--- | :--- |
| **Enabled APIs** | The connector calls the Admin SDK and Cloud Identity APIs, plus the Groups Settings API if you use group settings. The Admin SDK API must be enabled. See the table below for the others. |
| **Service account** | The single identity C1 authenticates as. It needs no project IAM role. |
| **JSON key** | The credential you upload to C1. Creating one requires the Service Account Key Admin role and an organization policy that permits key creation. |
| **Domain-wide delegation** | The Workspace-side grant that authorizes the service account's scopes. This is what actually lets the connector read and write directory data. |

<Note>
Domain-wide delegation is configured in the Google Admin console, not in Google Cloud. Granting the service account a Google Cloud IAM role does not give it access to Workspace data, and no project role is required for this connector.
</Note>

### Allow service account key creation

The connector authenticates with a JSON key, so your organization must permit key creation on this service account.

The `constraints/iam.disableServiceAccountKeyCreation` organization policy blocks key creation. **Google enforces this policy by default for organizations created on or after May 3, 2024**, so new organizations hit it unless an administrator grants an exception.

If the policy blocks you, key creation fails with:

```text
ERROR: (gcloud.iam.service-accounts.keys.create) FAILED_PRECONDITION: Key creation
is not allowed on this service account.
```

In the console, the **ADD KEY** option is unavailable and Google reports that service account key creation is disabled.

**Permissions to check:**

| Requirement | Details |
| :--- | :--- |
| IAM permission | `iam.serviceAccountKeys.create`, granted by the **Service Account Key Admin** role (`roles/iam.serviceAccountKeyAdmin`). The basic **Editor** role also includes it. |
| Organization policy | `constraints/iam.disableServiceAccountKeyCreation` must not be enforced on the project. A managed equivalent, `iam.managed.disableServiceAccountKeyCreation`, controls the same behavior. |
| Related policies | `constraints/iam.serviceAccountKeyExpiryHours` caps how long new keys stay valid. If your organization sets it, plan to rotate the key in C1 before it expires. |

Grant the key admin role to whoever creates the key:

```bash
gcloud iam service-accounts add-iam-policy-binding \
  c1-integration@YOUR_PROJECT_ID.iam.gserviceaccount.com \
  --member="user:admin@yourdomain.com" \
  --role="roles/iam.serviceAccountKeyAdmin" \
  --project=YOUR_PROJECT_ID
```

Check whether the organization policy is enforced on your project:

```bash
gcloud org-policies describe iam.disableServiceAccountKeyCreation \
  --project=YOUR_PROJECT_ID \
  --effective
```

If it is enforced, a user with the **Organization Policy Administrator** role (`roles/orgpolicy.policyAdmin`) can add a project-level exception. Save this as `policy.yaml`:

```yaml
name: projects/YOUR_PROJECT_ID/policies/iam.disableServiceAccountKeyCreation
spec:
  rules:
  - enforce: false
```

Then apply it:

```bash
gcloud org-policies set-policy policy.yaml
```

<Note>
This exception applies only to the project you name. Enforcement elsewhere in your organization is unchanged. If your organization manages exceptions with tags rather than per-project policies, see Google's [Organization policies and tags](https://cloud.google.com/resource-manager/docs/organization-policy/tags-organization-policy) documentation.
</Note>

<Warning>
Google recommends against long-lived service account keys and prefers Workload Identity Federation where it's available. This connector requires a JSON key, so treat it as a sensitive credential: store it in a secrets manager, never commit it to source control, and rotate it on a schedule. See Google's [best practices for managing service account keys](https://cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys).
</Warning>

## Grant domain-wide delegation in Google Workspace

Domain-wide delegation authorizes the service account to call Workspace APIs on behalf of your organization. Configure it in the Google Admin console.

<Steps>
<Step>
Go to [https://admin.google.com](https://admin.google.com) as a **SUPER ADMIN**.
</Step>
<Step>
In the navigation menu, select **Security** > **Access and data control** > **API Controls**.
</Step>
<Step>
Click **MANAGE DOMAIN WIDE DELEGATION**.
</Step>
<Step>
Click **Add new** and fill out the form:

   - **Client ID**: The service account's Unique ID
   - **OAuth Scopes**: Copy and paste in the relevant scopes from [OAuth scopes](#oauth-scopes) below
</Step>
<Step>

### OAuth scopes

Choose one of the two sets below. Read-only access lets C1 sync access data. Read/write access lets C1 sync access data and provision access.

<Tabs>
<Tab title="Read-only">
Paste this comma-separated list into the **OAuth Scopes** field:

```bash
https://www.googleapis.com/auth/admin.directory.domain.readonly, https://www.googleapis.com/auth/admin.directory.group.readonly, https://www.googleapis.com/auth/admin.directory.group.member.readonly, https://www.googleapis.com/auth/admin.directory.rolemanagement.readonly, https://www.googleapis.com/auth/admin.directory.user.readonly, https://www.googleapis.com/auth/admin.reports.audit.readonly, https://www.googleapis.com/auth/admin.directory.user.security, https://www.googleapis.com/auth/cloud-identity.inboundsso.readonly
```

| Scope | Purpose |
| :--- | :--- |
| `admin.directory.domain.readonly` | Identify the primary domain of the Google Workspace account |
| `admin.directory.group.readonly` | Read and sync Google Groups |
| `admin.directory.group.member.readonly` | Read and sync the members of each group |
| `admin.directory.rolemanagement.readonly` | Read and sync roles and their assignments |
| `admin.directory.user.readonly` | Read and sync users |
| `admin.reports.audit.readonly` | Sync usage and admin events for continuous sync. Also required to sync enterprise applications |
| `admin.directory.user.security` | Discover OAuth apps through per-user token listing. Also required to sync enterprise applications, and permits three actions that revoke a user's access. See the warning below |
| `cloud-identity.inboundsso.readonly` | Optional. Resolve SAML app IDs to stable identifiers. Without it, SAML app IDs fall back to display names |
</Tab>

<Tab title="Read/write">
Paste this comma-separated list into the **OAuth Scopes** field:

```bash
https://www.googleapis.com/auth/admin.directory.domain.readonly, https://www.googleapis.com/auth/admin.directory.group.readonly, https://www.googleapis.com/auth/admin.directory.group.member, https://www.googleapis.com/auth/admin.directory.rolemanagement, https://www.googleapis.com/auth/admin.directory.user, https://www.googleapis.com/auth/admin.reports.audit.readonly, https://www.googleapis.com/auth/admin.datatransfer, https://www.googleapis.com/auth/admin.directory.group, https://www.googleapis.com/auth/admin.directory.user.security, https://www.googleapis.com/auth/apps.groups.settings, https://www.googleapis.com/auth/cloud-identity.inboundsso.readonly
```

| Scope | Purpose |
| :--- | :--- |
| `admin.directory.domain.readonly` | Identify the primary domain of the Google Workspace account |
| `admin.directory.group.readonly` | Read and sync Google Groups |
| `admin.directory.group.member` | Write. Manage group memberships, adding or removing users from groups |
| `admin.directory.rolemanagement` | Write. Manage role assignments, granting or revoking roles |
| `admin.directory.user` | Write. Provision and deprovision accounts, update user profiles and custom-schema values, and promote and demote super administrators |
| `admin.reports.audit.readonly` | Sync usage and admin events for continuous sync. Also required to sync enterprise applications |
| `admin.datatransfer` | Write. Transfer user data between Google accounts |
| `admin.directory.group` | Write. Provision groups |
| `admin.directory.user.security` | Write. Discover OAuth apps, sync enterprise applications, and run actions that remove a user's access, such as sign out and deleting auth tokens and app passwords |
| `apps.groups.settings` | Write. Edit group settings. Requires the Groups Settings API |
| `cloud-identity.inboundsso.readonly` | Optional. Resolve SAML app IDs to stable identifiers. Without it, SAML app IDs fall back to display names |
</Tab>
</Tabs>

<Warning>
The write scopes let C1 provision and deprovision access. **If you do not want C1 to perform these tasks, use the read-only scope set.** Read-only still syncs users, groups, roles, and enterprise applications, so it is sufficient when you use Google Workspace as your [directory](#set-google-workspace-as-your-c1-directory) and run access reviews.

The read-only set has one exception. `admin.directory.user.security` appears in both sets, and it permits three actions that revoke a user's access: `sign_out_user`, `delete_all_oauth_tokens`, and `delete_all_application_passwords`. These actions remain available with the read-only set. **If you do not want C1 to perform these tasks, do not grant this scope.** The connector then stops discovering OAuth apps and stops syncing enterprise applications.
</Warning>

### Step 2: Create Kubernetes configuration files

Create two Kubernetes manifest files for your Google Workspace connector deployment:

#### Secrets configuration

```yaml expandable
# baton-google-workspace-secrets.yaml
apiVersion: v1
kind: Secret
metadata:
  name: baton-google-workspace-secrets
type: Opaque
stringData:
  # C1 credentials
  BATON_CLIENT_ID: <C1 client ID>
  BATON_CLIENT_SECRET: <C1 client secret>

  # Google Workspace credentials
  BATON_CUSTOMER_ID: <Your customer ID>
  BATON_DOMAIN: <Your primary domain>
  BATON_ADMINISTRATOR_EMAIL: <Your administrator email>

  # Paste the service account JSON key as a block scalar, indented under the pipe
  BATON_CREDENTIALS_JSON: |
    {
      "type": "service_account",
      "project_id": "<Your project ID>",
      "private_key_id": "<Your private key ID>",
      "private_key": "<Your private key>",
      "client_email": "<Your service account email>",
      "client_id": "<Your service account unique ID>"
    }

  # Optional: include if you want C1 to provision access using this connector
  BATON_PROVISIONING: "true"
```

`stringData` takes plain values, so no base64 encoding is required. Quote `"true"` so Kubernetes reads it as a string rather than a Boolean.

See the connector's README or run `--help` to see all available configuration flags and environment variables.

#### Deployment configuration

```yaml expandable
# baton-google-workspace.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: baton-google-workspace
  labels:
    app: baton-google-workspace
spec:
  selector:
    matchLabels:
      app: baton-google-workspace
  template:
    metadata:
      labels:
        app: baton-google-workspace
        baton: true
        baton-app: google-workspace
    spec:
      containers:
      - name: baton-google-workspace
        image: public.ecr.aws/conductorone/baton-google-workspace:latest
        imagePullPolicy: IfNotPresent
        env:
        - name: BATON_HOST_ID
          value: baton-google-workspace
        envFrom:
        - secretRef:
            name: baton-google-workspace-secrets
```

## Troubleshooting the Google Workspace integration

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| `FAILED_PRECONDITION: Key creation is not allowed on this service account` | The `iam.disableServiceAccountKeyCreation` organization policy is enforced, or you lack the Service Account Key Admin role. | See [Allow service account key creation](#allow-service-account-key-creation). |
| `Error 403: Request had insufficient authentication scopes` / `ACCESS_TOKEN_SCOPE_INSUFFICIENT` | The domain-wide delegation grant is missing scopes the connector needs. | Remove and re-add the API client with the full scope set. See [When adding permissions to my Google Workspace API Client permissions I get authorization errors](#when-adding-permissions-to-my-google-workspace-api-client-permissions-i-get-authorization-errors). |
| `unauthorized_client` when the connector authenticates | The Client ID in domain-wide delegation doesn't match the service account's Unique ID, or the requested scopes aren't authorized. | Confirm you entered the numeric **Unique ID**, not the service account email, and that the scope list matches exactly. |
| `SERVICE_DISABLED` or "API has not been used in project ... before or it is disabled" | The connector's API isn't enabled in the project. | Enable it. See [Enable the APIs](#enable-the-apis). |
| Authentication succeeds but the sync returns no users or `Not Authorized to access this resource/api` | The **Administrator email** isn't a super admin, or the **Customer ID** is wrong. | Confirm both values. See [Find your customer ID and primary domain](#find-your-customer-id-and-primary-domain). |
| The connector worked and then stopped authenticating | The service account key expired under `constraints/iam.serviceAccountKeyExpiryHours`, or someone deleted it. | Create a new key and upload it to the connector. |
